Content Scripts — Cheat Sheet

Registration syntax, the isolated-world rules, and exactly which APIs a content script can touch directly. Compressed from Lesson 3.

Mission Reference: Anatomy glossary Reference: Messaging & storage patterns Lesson 3: Content scripts

Registering one

"content_scripts": [
  {
    "matches": ["*://*.mozilla.org/*"],
    "js": ["content-script.js"],
    "css": ["styles.css"],
    "run_at": "document_idle",
    "all_frames": false
  }
]
KeyControls
matchesWhich URLs (as match patterns) trigger auto-injection. Required.
js / cssFiles to inject. Either or both.
run_atdocument_start (before DOM built), document_end (DOM built, resources may still load), document_idle (default — page mostly settled).
all_framesInject into every iframe (true) or just the top frame (false, default).

A statically declared content_scripts entry needs no separate host_permissions — matches is the grant. (Dynamic injection via scripting.executeScript() is different: that needs activeTab or explicit host permissions.)

The isolated world

A content script shares the page's live DOM but not its JS. It can read/write elements the page created, but window.someVarThePageSet is invisible to it, and vice versa — each gets its own global scope layered over the same document.[1]

Reloading the page re-injects the content script from scratch — nothing in its top-level scope survives navigation. Treat it as stateless; persist anything that matters via storage or a message to the background script.

APIs available directly (no messaging needed)

NamespaceWhat's available
storageEverything — get/set/remove, full access.
runtimesendMessage(), connect(), onMessage, onConnect, getURL(), getManifest().
i18ngetMessage(), getUILanguage(), detectLanguage().
extensiongetURL(), inIncognitoContext.

Everything else — tabs, notifications, cookies, bookmarks, etc. — is not reachable from a content script. Message the background script and have it call the API.[2]

Talking to the background script

// content script
browser.runtime.sendMessage({ type: "link-clicked", url: link.href });

// background script — top-level, synchronous
browser.runtime.onMessage.addListener((message) => { /* ... */ });

Background → content script (needs a specific tab):

browser.tabs.sendMessage(tabId, { type: "hello" });

Talking to the page's own scripts

Not via runtime messaging — use window.postMessage on both sides, and always check event.source === window before trusting anything (the page is untrusted input):

// content script, listening
window.addEventListener("message", (event) => {
  if (event.source !== window) return;
  // handle event.data
});

Where content scripts can't run

Browser UI (about:* pages, the PDF viewer), and a short list of sensitive domains including addons.mozilla.org and accounts.firefox.com. If a content script seems to silently not fire, check the URL against this before debugging the code.[3]
