Messaging & Storage Patterns

The connective tissue between background scripts, popups, and options pages. Compressed from Lesson 2.

Mission Reference: Anatomy glossary Lesson 2: Background, permissions, popup, options

Ask the background script for something

From a popup, options page, or content script:

const answer = await browser.runtime.sendMessage({ type: "some-request" });

In the background script — register it top-level and synchronously, never inside a callback, or it won't survive the script unloading and reloading:

browser.runtime.onMessage.addListener((message) => {
  if (message.type === "some-request") {
    return Promise.resolve("some answer"); // returning a Promise = async reply
  }
});

Persist a setting

Prefer storage.sync for user settings (syncs across the user's devices) over storage.local. Never hold state in a plain JS variable in a background script — Manifest V3 background scripts are non-persistent and can unload between events, wiping globals.[1]

// write
await browser.storage.sync.set({ greeting: "Hello!" });

// read, with a default if nothing's saved yet
const { greeting } = await browser.storage.sync.get({ greeting: "Hello!" });

Open the options page from code

browser.runtime.openOptionsPage();

Works from a background script, popup, or any extension page. There's no equivalent for opening a popup programmatically — popups only open in response to the user clicking the toolbar button.[2]

Permissions these patterns need

API usedPermission string
browser.storage.*"storage"
browser.tabs.* (most methods)"tabs"
Any URL-based access (host_permissions, MV3)match pattern, e.g. "*://example.com/*"

runtime.sendMessage, runtime.onMessage, and runtime.openOptionsPage need no permission — runtime is always available.

Notes & sources

  1. MDN, Background scripts — event pages must use the storage API instead of globals, and register listeners synchronously at the top level.
  2. MDN, Popups — a popup cannot be opened programmatically, only via user action.
