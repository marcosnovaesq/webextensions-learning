External Requests — Cheat Sheet

Who's allowed to fetch what, and the one gotcha that catches everyone. Compressed from Lesson 4.

Mission Reference: Content scripts cheat sheet Lesson 4: Talking to external servers

Where does the fetch get its privilege?

Contexthost_permissions gets you...
Background scriptFetch/XHR to matching origins, no CORS involved at all.
Popup / options pageSame as background — any extension page is privileged.
Content script (MV3)Nothing extra — follows the host page's own CORS policy.[1]

Rule of thumb: if a network call needs to reach somewhere the page itself couldn't, do it in the background script and message the result over, exactly like Lesson 3's rule for tabs and other restricted APIs.

Declaring the permission

"host_permissions": ["https://api.example.com/*"]

Match pattern, same syntax as a content script's matches. Narrow it to the real domain — a wildcard like *://*/* here is a much bigger grant than the equivalent in content_scripts, since it applies to genuinely unrestricted cross-origin requests, not just injection.

The fetch error-handling gotcha

fetch() rejects only on a network-level failure. An HTTP error status resolves normally — check response.ok yourself:[2]

const response = await fetch(url);
if (!response.ok) {
  throw new Error(`Request failed: ${response.status}`);
}
const data = await response.json();

Thrown inside a browser.runtime.onMessage listener, this becomes a rejected promise for whoever called sendMessage() — wrap that call site in try/catch too.

Storing what comes back

storage.local/storage.sync are ordinary browser storage — fine for caching a public response, not an encrypted vault for a real credential. See Lesson 4.

When the API needs to know who you are

Public, unauthenticated APIs: just fetch. A service that needs a specific logged-in user's authorization (Google, GitHub, etc.): that's the identity API — identity.launchWebAuthFlow() plus identity.getRedirectURL() as the OAuth2 callback. Not covered hands-on yet.
