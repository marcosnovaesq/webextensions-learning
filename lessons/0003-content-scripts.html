Content Scripts

The isolated world

A content script shares the page's live DOM — it can read and modify exactly what's on screen, same as the page's own scripts — but it does not share the page's JavaScript. Each gets its own separate global scope layered over the same document.[1]

// page-script.js (the site's own code)
window.foo = "from page";

// content-script.js (your extension's code, same page)
console.log(window.foo); // undefined — different world entirely

This cuts both ways: the page can't see your content script's variables either, and if the page redefines something like window.confirm, your content script still sees the browser's real, original version — not the page's tampered one. It's a safety boundary, not a bug.

One more consequence: reloading or navigating the page re-injects the content script from scratch. Nothing in its top-level scope survives — treat it as stateless, and persist anything that matters via storage or a message to the background script.

What a content script gets for free

Unlike a popup, options page, or background script, a content script does not get the full WebExtensions API surface. It gets a short, fixed allowlist directly — storage (full access), plus slices of runtime (sendMessage, connect, getURL, …) and i18n. Everything else — tabs, notifications, cookies, bookmarks, all of it — is off-limits directly. To use any of those, the content script has to message the background script and have it make the call.[2]

Worth flagging against last lesson's habit: storage is directly usable from a content script, exactly like from the popup or options page. Messaging isn't a mandatory funnel for state — it's specifically for the APIs a content script can't reach on its own.

Registering one

"content_scripts": [
  {
    "matches": ["*://*.mozilla.org/*"],
    "js": ["content-script.js"],
    "run_at": "document_idle"
  }
]

matches is a list of URL patterns — the content script only injects on pages that match. Unlike programmatic injection (scripting.executeScript()), a script declared this way in the manifest needs no separate host_permissions entry: matches is the grant.[3] Full key reference in the cheat sheet.

Build it: link-click-logger

Starter scaffold at experiments/0003-link-click-logger/: a content script that watches for link clicks on any page, a background script that tallies them in storage, and a popup that shows the running count. Same shape as Lesson 2's round trip, one new leg added on the front.

TODO 1 — content-script.js

Listen for clicks anywhere on the page. When the click lands on (or inside) an <a>, message the background script with the link's URL.

Reveal 
document.addEventListener("click", (e) => {
  const link = e.target.closest("a");
  if (!link) return;
  browser.runtime.sendMessage({ type: "link-clicked", url: link.href });
});

TODO 2 — background.js

Listen for those messages; keep a running count and the last URL in storage.sync.

Reveal 
browser.runtime.onMessage.addListener(async (message) => {
  if (message.type === "link-clicked") {
    const { linksClicked = 0 } = await browser.storage.sync.get("linksClicked");
    await browser.storage.sync.set({
      linksClicked: linksClicked + 1,
      lastUrl: message.url,
    });
  }
});

TODO 3 — popup/popup.js

Read the count and last URL straight from storage.sync — no messaging needed here.

Reveal 
document.addEventListener("DOMContentLoaded", async () => {
  const { linksClicked = 0, lastUrl = "—" } =
    await browser.storage.sync.get(["linksClicked", "lastUrl"]);
  document.getElementById("count").textContent = linksClicked;
  document.getElementById("last-url").textContent = lastUrl;
});

Run it

  1. about:debugging#/runtime/this-firefox → Load Temporary Add-on… → select experiments/0003-link-click-logger/manifest.json.
  2. Go to any ordinary site (not addons.mozilla.org or an about: page — content scripts can't run there) and click a few links.
  3. Open the popup — the count should reflect your clicks, even across different sites, since storage is shared extension-wide.
  4. In about:debugging, click Inspect next to the extension to open a console on the page itself and watch the content script's messages fire live.
