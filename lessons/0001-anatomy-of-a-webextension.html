Lesson 1 · WebExtensions

The Anatomy of a WebExtension

Every extension, no matter how small, is built from the same short list of parts. Learn the parts and the map, and any extension's codebase — including shuff's — stops being a pile of files and becomes something you can navigate.

Mission Reference: Glossary Primary source: MDN

Primary source for this lesson: MDN — Anatomy of a WebExtension. Everything below is a compressed, quizzed version of that page — read the original when you want the full detail.

An extension is just a folder of files, packaged up for installation. There's no framework, no build step required, no runtime magic — the browser reads a folder and does what it's told.[1] Almost everything in that folder is optional. Exactly one file is not.

The one required file

Every extension has a manifest.json — and nothing else is mandatory. It carries basic metadata (name, version) and, more importantly, it's the hub: every other component gets wired in by pointing to it from the manifest.[1]

Everything hangs off manifest.json — nothing on the outside is required.

Two worlds: privileged vs. page

The components split cleanly into two groups, and the split matters more than any individual name.

Privileged (extension) context — background scripts, popups, sidebars, options pages, and any other "extension page." These get full access to WebExtensions APIs like tabs or storage, gated by what's declared in permissions.[2]

All of these are just HTML documents — CSS and JS included, like any web page — referenced from the manifest. A popup opens on a toolbar-button click and closes when focus leaves it. A sidebar pins into the browser's left pane and survives navigation. An options page opens inside the browser's own add-ons manager. Functionally near-identical; the difference is only when and where the browser shows them.[3]

Page context — content scripts. These run inside a real web page's DOM, in an isolated JS world separate from the page's own scripts. They can read and modify the DOM freely, but only get a small subset of WebExtensions APIs directly — for the rest, they message the background script.[4]

One more piece connects the two worlds: web accessible resources. An extension's packaged images/CSS/JS aren't reachable from a web page by default — a content script has to explicitly expose them via web_accessible_resources before it can, say, insert a bundled icon into the page.[5]

shuff defines an action popup only — action.default_popup points at popup/shuff.html, which right now just says "Hello!". There's no background key (no background script), no content_scripts, no options_ui, no icons, and no permissions. Whatever shuff ends up doing, the first real design question will be: does that logic belong in the popup, a background script, or a content script?
