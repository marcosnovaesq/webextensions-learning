Talking to External Servers

Every component from Lesson 1's map is now built with something real — but none of it has left the browser yet. Most extensions that do anything useful eventually call an outside API, and an extension's relationship to that outside world is genuinely different from a normal webpage's. Today: where a network call is allowed to be privileged, where it isn't, and a fetch that actually leaves the machine.

Mission Lesson 3 Reference: External requests cheat sheet

Primary sources for this lesson: host_permissions · Content scripts — XHR and fetch · Using Fetch — all on MDN.

Four facts worth knowing before you build

A background or extension-page fetch to a host in host_permissions is unrestricted — no CORS involved at all. MDN states it plainly: those APIs get "access to those origins without cross-origin restrictions."[1] That's a different mechanism from a webpage's own fetch(), which only works cross-origin if the server opts in with CORS headers. Here, the browser grants the access instead, based on a permission the user approved — the server's own headers don't come into it.

That privilege does not reach content scripts. As of Manifest V3 (Firefox 101+, Chrome 73+), a content script's fetch() is subject to the exact same CORS policy as the page it's injected into — host_permissions only works in extension pages (background, popup, options), not content scripts.[2] Practical rule: put outbound API calls in the background script, not a content script, the same way Lesson 3 put tabs calls there.

fetch() only rejects its promise on a network-level failure — offline, DNS failure, a bad scheme. An HTTP error status like 404 or 500 still resolves the promise with a normal Response object. You have to check response.ok (or .status) yourself and throw explicitly, or a try/catch around the fetch will silently never catch the failure.[3]

storage.local and storage.sync are not a credentials vault. They're plain browser storage, offering the same protection as the rest of the browser profile — fine for caching a public API's response, but worth being deliberate about before putting a real user's API token or password there.

Build it: advice-fetcher

Starter scaffold at experiments/0004-advice-fetcher/: a popup with a button, and a background script that fetches a random line of advice from a small public API (api.adviceslip.com, no key required). Same shape as before — message out from the popup, do the privileged work in the background, message the result back.

TODO 0 — manifest.json

Add a host_permissions entry for api.adviceslip.com, so the background script's fetch to it is unrestricted. There's also a trivial local server at server.js (run with node server.js) serving the same response shape at localhost:8787, with a /advice/broken endpoint that always 500s — useful later for testing the error path on demand instead of temporarily breaking the real URL. Grant both now so either target works.

Reveal 
"host_permissions": [
  "https://api.adviceslip.com/*",
  "http://localhost:8787/*"
]

TODO 1 — background.js

Listen for a { type: "get-advice" } message. Fetch https://api.adviceslip.com/advice, check response.ok before trusting the body, parse the JSON, and return the advice text (the response shape is { slip: { advice: "..." } }). If anything goes wrong, throw — a thrown error in a message listener becomes a rejected promise for whoever sent the message.

Reveal 
browser.runtime.onMessage.addListener(async (message) => {
  if (message.type === "get-advice") {
    const response = await fetch("https://api.adviceslip.com/advice");
    if (!response.ok) {
      throw new Error(`Advice API responded with ${response.status}`);
    }
    const data = await response.json();
    return data.slip.advice;
  }
});

TODO 2 — popup/popup.js

On button click, message the background script and show the result. Wrap it so a rejected promise (the throw above) shows an error message instead of leaving the popup stuck on "Loading…".

Reveal 
document.getElementById("get-advice").addEventListener("click", async () => {
  const out = document.getElementById("advice");
  out.textContent = "Loading…";
  try {
    out.textContent = await browser.runtime.sendMessage({ type: "get-advice" });
  } catch (error) {
    out.textContent = `Couldn't fetch advice: ${error.message}`;
  }
});

Run it

  1. about:debugging#/runtime/this-firefox → Load Temporary Add-on… → select experiments/0004-advice-fetcher/manifest.json.
  2. Open the popup, click the button a few times — you should see a new line of advice each time.
  3. To see the error path fire, on demand and repeatably: run node server.js in a terminal, change background.js's fetch URL to http://localhost:8787/advice/broken (always a 500), reload the extension in about:debugging, and click the button again. You should see the error message, not a stuck "Loading…". Point the URL at http://localhost:8787/advice to see the happy path against the local server instead, or back at the real API when you're done.
  4. In about:debugging, click Inspect next to the extension to open a console on the background script and watch the fetch happen.

Beyond this lesson: when the API needs to know who you are

Everything above assumes a public, unauthenticated API. The moment an extension needs to act as a specific logged-in user against a service like Google or GitHub, that's an OAuth2 flow, and the relevant piece is the identity API — identity.launchWebAuthFlow() opens the provider's login/consent screen and hands back a token, using identity.getRedirectURL() as the callback address. Not built hands-on today (it's a bigger surface, with real per-provider differences and a Firefox/Chrome redirect-URL split worth its own lesson) — flagged here so the vocabulary is there when shuff or something else needs it.

Back to shuff

shuff hasn't needed an external server yet, but the moment it does — checking a URL against a blocklist API, syncing settings to something other than storage.sync, anything — this is the shape: host_permissions for the domain, the fetch itself in the background script, and a response.ok check standing between "it works on the happy path" and "it works."
